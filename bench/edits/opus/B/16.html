Summary

At 14:02 UTC a configuration change lowered the Billing API's database connection pool from 200 connections to 20. With far fewer connections available, requests queued waiting for a connection and timed out, driving the error rate as high as 38.5%. Once pool exhaustion was identified, the change was rolled back and errors returned to baseline by 14:49.

Root cause

The change set the connection pool size to 20, a tenth of its previous value of 200. Under normal afternoon load the Billing API needs far more concurrent database connections than that, so requests waited for a free connection until they hit their timeout. The database itself stayed healthy throughout; the bottleneck was entirely in the application's pool. Nothing in review or deployment flagged the new value as unsafe.

Contributing factor The config linter did not validate bounds on the connection pool size, so a value of 20 passed every automated check.
