The dispatch-jobs queue is backing up

Owner: Dispatch Engineering

Never purge dispatch-jobs Every message in the queue is a real customer delivery. Purging it loses deliveries that cannot be recovered. Move a bad message to the dead letter queue instead (step 2).
Symptoms Diagnose Fix steps Escalation

Symptoms

> 5000depth for 10 minutes fires QUEUE_DEPTH_HIGH
< 400normal queue depth
200database connection pool cap
  • The QUEUE_DEPTH_HIGH alert fires when depth stays above 5000 for 10 minutes. Normal is under 400.
  • Drivers see new jobs arrive late in the app.

Diagnose

  • Check the queue depth and consumer count: 
    kubectl -n dispatch get hpa dispatch-consumer
  • Look at the oldest message age on the queue dashboard.
  • Check the database connection pool. It is capped at 200 connections.

Fix steps

  1. Scale the consumers

    1. Run: 
      kubectl -n dispatch scale deploy dispatch-consumer --replicas=24
    2. Wait 5 minutes and re-check.
    3. If depth is still rising, scale to 40. That is the maximum the database pool supports. 
      kubectl -n dispatch scale deploy dispatch-consumer --replicas=40

  2. Check for poison messages

    1. Look for a message that has been retried more than 10 times.
    2. If there is one, move it to dispatch-dlq with the dlq-move tool.

  3. Pause the bulk import scheduler

    Do it in the admin console. Bulk imports add up to 3000 jobs at a time.

  4. Re-enable the scheduler gradually

    Wait until depth drops under 400.

Escalation

If depth is still above 5000 after 20 minutes, page the Dispatch Engineering lead and open an incident in #incidents.
