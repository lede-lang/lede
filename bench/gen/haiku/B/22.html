Choosing a message queue for order routing

Fulfillment, Saltmarsh Foods. Decision page for the architecture review on 2026-10-21.

Expected load

Peak load is 1,800 messages per second, with an average of 400. Messages are under 8 KB. At-least-once delivery is acceptable. Ordering is needed only within a single order, not across the whole stream.

Options

  • SQS: a fully managed queue service, with FIFO queues that keep order within a message group.
  • Kafka (Amazon MSK): a managed log with partitions, long retention and replay.
  • RabbitMQ (Amazon MQ): a managed broker with flexible routing and per-queue ordering.

Pros and cons

SQS

  • Pro: fully managed, and it scales automatically.
  • Pro: FIFO queues keep order per order ID at a low cost.
  • Con: no replay once a message is consumed.
  • Con: messages are limited to 256 KB. Our payloads are well under that.

Kafka (Amazon MSK)

  • Pro: replay and stream processing.
  • Pro: very high throughput per partition.
  • Con: needs partition planning up front.
  • Con: we would own broker upgrades.

RabbitMQ (Amazon MQ)

  • Pro: flexible routing rules.
  • Pro: familiar to several teams.
  • Con: we would own capacity planning.
  • Con: the cost is more than double SQS.

Recommendation

Recommended: SQS with FIFO queues keyed by order ID SQS gives per-order ordering with no broker to run, at the lowest cost of the three options. We will revisit this choice if the analytics team needs event replay in 2027, since SQS cannot provide it.
